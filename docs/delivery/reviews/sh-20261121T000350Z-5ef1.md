**Summary (the architect's).** ADR-0045 builds on machinery that mostly exists: the operator gate check (`_operator_step_refusal`), the `--kind mac` worktree, `rests_on`, and merge-ok inherited by close. Two of its promises have no data behind them. First, nothing records which head an operator-machine run was at: gate files have no head field and suite rows record no sha. So D3's refusals cannot enforce D2's 'a new run per head' (F01). Second, the queue keeps only the latest verdict per task, so D3's 'the record at <old> held it as a pass' cannot be checked after two integration merges in a row (F02). Both need the operator's decision before D2 and D3 are tasked. The rest is preparatory work: the §15.4 evidence rules, including the very example D3 forbids, are copied into six places (F03); the check grammar is split in two places and its consumers would grow to five (F04); reading a file at a rev is done five ways (F05); and the three merge-time judges build their refusal lists separately, with `ccp verify check` already weaker than merge-ok (F06). Friction notes: confirmed the 0198 note that checks run `ccp` from PATH (F09; 16 check steps in tasks 0190-0209 do) and the 0199 wa-03 note on wording greps (F10). For the two leak-check notes, I confirmed the mechanism: `scripts/leak-check.sh` runs `git grep` over the whole tree against an untracked, machine-local denylist, so a denylist edit, or a hit that came in from main, fails every in-flight task's `ccp docs check` and the gate's plane-docs stage. I could not see the hit itself (the denylist is private) and left it out because the ADR does not touch it: one finding left out.
