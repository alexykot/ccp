# Delivery-log templates

Templates for a product's `docs/delivery/`, the **durable task log** (plane SPEC §4.2, §5). The
plane's README quick start copies them; this file is not copied.

The task log lives in the product's git and is permanent: tasks are never deleted, and their status
and notes stay in history. It sits beside `docs/PROJECT.md` and `docs/SPEC.md` (or `docs/spec/`),
which the lead (the design seat) owns, with the operator for PROJECT.

Runtime state (leases, runs, waits, questions, credential status) lives in the queue,
`.delivery-queue/<project_id>/`, outside the product's git (see `queue/README.md`). Never put it in
the task log.

## Files

| Template | Copy to | What it is |
| --- | --- | --- |
| `TEMPLATE-task.md` | `docs/delivery/TEMPLATE-task.md` | the canonical task format (SPEC §5); copy it for each new task |
| `WRITING-tasks.md` | `docs/delivery/WRITING-tasks.md` | the product's own task-writing rules; the generic ones are the plugin's `writing-tasks` skill |
| `standing-dod.md` | `docs/delivery/standing-dod.md` | the definition of done every task carries: the plane's items, then the product's |
| `example-plane.json` | `docs/delivery/plane.json` | the product's `ccp` settings (SPEC §8.1); only `project_id` is required |
| `example-tasks/`, `example-INDEX.yaml` | — | examples of the format, not anyone's work |

The plugin ships the agents, skills, hooks and orientation: a product holds no managed copy of them
(SPEC §9.5). Product-specific additions to the plane's instructions go in a product-owned file, such
as `docs/delivery/LOCAL.md`.

## Layout in the product

```
docs/delivery/
  plane.json         # product-owned ccp settings; its presence opts in to ccp
  WRITING-tasks.md
  standing-dod.md
  TEMPLATE-task.md
  INDEX.yaml         # generated by `ccp tasks index`; never hand-edited
  reviews/           # durable review and shaping records (SPEC §19)
  tasks/
    NNNN-<slug>.md
```

## Who writes what

- The lead, as task-log owner, writes new task files and keeps their refs accurate. As spec
  maintainer (SPEC §17) it may edit PROJECT, the SPEC and a task's `## Context (not checked)`.
- The runner and the verifier append implementation and verification notes.
- `ccp tasks close` writes `status: done`. A task file carries `pending`, `done` or `dropped` only.

Each task has `depends_on` in its frontmatter (never only inside a check), `spec_refs` cited in its
text, and `dod_checks` the verifier can walk (setup, steps, expect).

## Task file names

`docs/delivery/tasks/NNNN-<kebab-slug>.md`, where `task_id` is the stem.

- `NNNN` is a zero-padded four-digit sequence in intended run order. Never reuse or renumber one;
  append the next free number.
- The slug is short and descriptive. A slice tag may sit in it (`0001-s1-…`) but never replaces
  `NNNN` as the sort key.
- `ccp tasks check` fails when `INDEX.yaml` is stale; rebuild it with `ccp tasks index`.
